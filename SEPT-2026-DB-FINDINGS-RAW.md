## Sync-worker resilience to an IFL source-database wipe / identity-reset (and to the go-live repoint)

The sync worker has NO concept of a source epoch and is structurally blind to an id reset. The reader watermark is `MAX(src_id)` read live out of our own raw table, and the reader asks IFL for `id > watermark - 500`; when the source id space restarts below that number, the query legitimately returns zero rows and the pass records `outcome='success'`, forever, with no error, no DQ finding, and `/api/live` still reporting health `ok`. The "CDC-safe watermark" ARCHITECTURE §7 claims is real for late inserts and small reseeds and useless for a reset: the overlap window is 500 rows against a 142,511-row cliff, and the schema fingerprint hashes only column names/types, so a wipe-and-recreate with the same schema is byte-identical (proved: sack1_TP1U2's fingerprint is the SAME across the July and September copies). The system survives the actual 11 Jul 2026 event only by luck — IFL also renamed `Source` to `MachineNo`, which trips the fingerprint gate loudly — and the documented cutover in DEPLOY.md is wrong in a way that would produce a permanent, silent, total blackout the moment that luck runs out.

There is no epoch, generation or source-instance concept anywhere in the codebase. `grep -rniE "\\bepoch|\\bgeneration\\b|source_epoch|watermark[ _]?reset|id.?reset"` over sms/**/src and db/migrations returns only unrelated hits (epoch-ms timestamps, `generation` in a doc comment). The failure is heterogeneous per stream, which makes it harder to spot, not easier:

The consequence of a flowing reject stream over a frozen cone stream is that every derived rate is nonsense: the reject-rate numerator grows while the denominator is frozen at the July total.

**Implication:** On a live plant this is a permanent, silent, total data blackout that presents as "the line is idle". Requirement 4 (reject history/trends), requirement 2 (cone weights), requirement 6 (sack logging) all show frozen or corrupted numbers with no indication that anything is wrong. IFL's first review already called the app "not live"; this is the mechanism by which it would become permanently not-live without anyone noticing.

**Recommendation:** Introduce an explicit source epoch. Minimum viable version: on every pass, before reading, compare the stored watermark to `SELECT MAX(id) FROM <sourceTable>`; if the source max is BELOW our watermark, halt that stream with a CRITICAL dq_finding (`source_id_regression`) exactly the way the fingerprint gate halts on drift — never read, never claim success. Fuller version: add `source_epoch_id` to sms_raw and sms.* keyed on a fingerprint of (source db create_date, MIN(id) row's timestamp), make the raw unique index `(line_id, source_epoch_id, src_id)`, and derive the watermark per epoch. `sys.databases.create_date` on the source is a free, read-only epoch discriminator that needs no write to IFL's DB.

Answering the question directly: yes — a genuinely new cone with source_row_id = 5 is silently dropped when canonical already holds a different cone with source_row_id = 5 from the previous epoch. It is dropped at persistRaw before it ever reaches the transform, and would be dropped again at existingSourceIds if it did. Neither drop is counted, logged, or turned into a dq_finding; `written` simply comes back lower than `read` and nothing compares the two.

The `minSourceRowId` bound added for performance (persistCanonical.ts:22-30) rests on the comment "source ids are monotone, so nothing below the batch minimum can match" — the exact invariant a reset destroys. **Implication:** Even if the reader were fixed to re-read from id 1 after a reset, the persistence layer would throw the new epoch away twice over. Fixing the watermark alone is not sufficient — it would turn a silent blackout into a silent discard, which looks identical from the UI.

**Recommendation:** Any epoch fix must reach all three places together: the raw unique index (add source_epoch_id), persistRaw's seen-set, and existingSourceIds' predicate. Separately and independently of the epoch work: make `read > 0 && written === 0` on a stream emit a WARNING dq_finding — that single check would have made every drop above visible.

### [MEDIUM] The @error / @errorMsg OUTPUT convention is unsafe: never reset on success, and @errorMsg has no default

**Evidence:** In all 13 procs @error and @errorMsg are assigned ONLY inside error branches. AddBlend's success path (pdas_procs_july.txt:33-38) inserts, sets @blendId, logs and `RETURN @blendId` without touching @error or @errorMsg; the same shape holds for AddCount (:78-84), AddTubeType (:146-152), CreateMaterial (:232-250), CreatePallet (:320-338), both Set* procs (which `RETURN 0`, :582 and :625) and all six GetAll* (which `RETURN (SELECT COUNT(*) ...)`). Declared defaults from the module text: `@error int = 0 OUTPUT` has one; `@errorMsg nvarchar(255) OUTPUT` has NONE in any of the 13; `@blendId int = -1 OUTPUT`/`@countId`/`@typeTypeId` have one, but CreateMaterial's `@materialId int OUTPUT` (:175) and CreatePallet's `@palletId int OUTPUT` (:273) do not. (Note: sys.parameters.has_default_value reads False for every parameter here, but that column is only populated for CLR procedures — the module text is authoritative for T-SQL.)

Two distinct traps. First, a caller that reuses one @err variable across several calls will see the PREVIOUS call's error code after a successful one, because success never clears it — the only safe pattern is to re-initialise before every call, or to ignore @error entirely and branch on the RETURN value. Second, @errorMsg is a required parameter everywhere, and @materialId/@palletId are required on the two Create procs, so the 'minimal' call that a reader might infer from the optional-looking OUTPUT parameters will fail with 'Procedure expects parameter which was not supplied'. The RETURN convention is also overloaded three ways: -1 = error; a positive new identity = Add*/Create* success; 0 = Set* success; a row count = GetAll* success.

**Implication:** Any client code we write against these procs is easy to get subtly wrong in a way that reports success as failure or vice versa. This is the kind of defect that surfaces in production and not in a single-call test.

**Recommendation:** If the write path is approved, wrap each proc in a single typed helper that declares fresh OUTPUT variables per call, always supplies @errorMsg and the id OUTPUT, and branches on RETURN_VALUE first (< 0 = failure) and only then reads @error/@errorMsg for the message.

### [HIGH] Retention and backup policy to put to IFL, and the risk if the worker is offline across a rebuild

**Evidence:** Retention observed, not asserted: DATA_TP1U2 created 2026-06-18 12:06:52 (sys.tables), wiped 2026-08-05 18:54:50 (wide tables recreated, raw tables reseeded to id 1). 48 days. The July copy holds 19 days at the moment of snapshot; the September copy holds 34 days at the moment of snapshot. There is no rolling-window purge — a purge leaves ids intact, and these restart at 1.

The risk asymmetry is the point, and it is why a normal retention conversation is not enough. Under a rolling purge, a worker offline for N days loses at most N days beyond the window, and the loss is bounded and predictable. Under THIS failure mode — drop and recreate — the loss is not bounded by the outage at all. Everything since the previous rebuild goes at one instant, however recently the worker last ran. A worker offline for one hour that happens to straddle the upgrade loses whatever the upgrade deleted; last time that was 26 days, 6,808 sacks and ~170,000 cone weighings. The 'retention window' IFL would quote (none) and the exposure (everything back to the last rebuild) are different quantities.

Our own exposure compounds it: after such a rebuild the sync worker either halts on schema drift (needing a human) or freezes silently on the stale watermark (needing nobody to notice), so the sidecar stops being an archive at precisely the moment it becomes the only one.

**Implication:** Sidecar continuity is not a nice-to-have operational metric on this project. It is the only thing standing between IFL and the permanent loss of their production history, and it currently has neither an automatic guard nor an off-machine backup.

**Recommendation:** Four asks to IFL, in priority order. (1) Notify us before any vendor maintenance, upgrade or reinstall touching DATA_TP1U2 — this is the whole ballgame and costs them nothing. (2) A nightly SQL Server backup of DATA_TP1U2 held by IFL and retained 90 days, so a rebuild is recoverable independently of us. (3) Confirm whether a backup predating 5 August exists; if it does, the 26 days are recoverable. (4) Agreement that the sidecar is the system of record for history older than the current source generation, which is already true in fact.

Four things we own. (a) Backup sms_real and the two archive MDF sets off this workstation today. (b) Sidecar backup policy: full weekly plus daily differential, retained 12 months, written to a second machine — the app DB is small (204k rows) so this is minutes. (c) The watermark-regression guard from the previous finding, so a rebuild is loud. (d) Per-feed data-freshness alerting, so a rebuild that freezes one feed is noticed within days rather than at the next quarterly report. Note (b) and (d) also protect the go-live cutover, when repointing IFL_DB_SERVER at the live database will present a source whose ids restart at 1 relative to our July-copy watermarks — the same regression, on purpose, on day one.
