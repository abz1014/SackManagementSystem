# Troubleshooting {#troubleshooting}

In the messages quoted below, `${span}` and `${since}` are placeholders: SMS replaces each with an actual time or duration when it shows the message.

| Symptom | Likely cause | Fix |
|---|---|---|
| Line's headline reads [[has had no readings for ${span} — the line, or the plant's data recorder, may have stopped]] on a line you know is running | The ~18-minute acquisition lag (see {{ref:lag}}) — the newest reading has not arrived yet, which is normal, not a fault. | Check the lag sentence under the top bar first. If the stated lag is much larger than usual, treat it as the next row instead. |
| The lag sentence reads [[No new readings since ${since} — the plant link may be down.]] | The sync worker has not delivered a new reading recently — a real connectivity or service problem, not the normal acquisition lag. | Check `SMS-Sync` is running. Check [[Health]]'s sync block for the failing table. Check the plant's own SQL Server is reachable from this machine. |
| `sync` halts, reporting an unregistered source generation | IFL's source tables were rebuilt (dropped and recreated with identities restarted) — a new generation. This is expected behaviour, not a bug — see {{ref:generations}}. | Run `node cli/dist/index.js epoch:list` to see it, then `epoch:accept` for it as in {{ref:install-first-connection}}. Never assume the new generation is a continuation of the old one. |
| Sign-in fails with a generic error for everyone, including known-good accounts | [[That username and password did not match.]] is shown for a wrong password, but also — per a known, open gap — for some database-connection failures, which look identical on screen. | Check `GET /api/health` and the plant/app database connectivity before assuming every account's password is wrong. |
| `sqlcmd`/the app cannot reach the app database at all | `APP_DB_SERVER`/`APP_DB_PORT` wrong, SQL Server Express not running, or a firewall blocking the app database port. | Confirm the SQL Server service is running and reachable with `sqlcmd` directly using the same server/port/login as `.env`. |
| PDF export fails or the [[Export PDF]] button errors | Microsoft Edge is not installed, or not at the path SMS expects. | Install Edge, or set `PDF_EDGE_PATH` to its actual location. |
| [[Health]]'s Backups block reads [[No backup file was found.]] | `BACKUP_DIR` does not match where the backup script actually writes, or no backup has run yet. | Confirm `BACKUP_DIR` in `.env` matches `-OutDir` in the backup script/scheduled task exactly, and that the scheduled task from {{ref:install-scheduled-tasks}} has actually run once. |
| `retention --dry-run` or a real `retention` run reports far more or fewer rows than expected | Retention only prunes `sms.sync_run` (default 90 days, newest row per line/table always kept) and non-CRITICAL `sms.dq_finding` (default 365 days) — never readings, `sms.audit_log`, or `sms.product_change`. | Confirm you are reading the right table's figures; see Appendix A for the two retention keys. |
| `cutover --confirm` refuses with exit code 2 | The required `--backup=<path.bak>` flag was left off — DEPLOY.md's own shorthand omits it, but the code requires it. | Always include `--backup=<path to a .bak file>` — see Appendix B. |
| `user:create` refuses with an invalid-role error | An old role name (`operator`, `supervisor`) was used. | Use exactly `viewer`, `engineer`, `manager` or `admin`. |
| A screen shows a [[Simulator]] label, or a sentence saying the figures shown are the plant simulator's and not the plant's, on what should be the live plant | The installation is pointed at a demonstration/simulator database, not the real plant. This should never appear on a live installation. | Confirm `IFL_DB_SERVER`/`IFL_DB_NAME_DATA`/`IFL_DB_NAME_PDAS` in `.env` point at the plant's own server and databases, not a `_SIM` copy. |
| A DQ finding or a "needs attention" state appears on [[Health]] that you do not recognise | See the [[Sync health]] and DQ blocks on [[Setup]] for which table and which finding. | Read the finding's own stated text — SMS states in words what it could not do and why, rather than a bare error code. If the cause is still unclear, it is a question for whoever maintains SMS's own code, not something this guide can resolve generically. |
| Weight basis or shift-boundary figures look wrong for this plant | `WEIGHT_BASIS`/`SHIFT_MODE` are not yet confirmed by IFL for every plant — see Appendix C, item 12. | Do not change these keys without a written answer from IFL; the app states plainly wherever this is unconfirmed. |
| [[Health]] stays at [[Something needs attention.]] because of a data finding that is real and needs no action (for example a recorded weight of exactly 0) | Known data findings do not clear themselves. | An engineer (rank 2 or above) opens the finding under [[Data quality findings]], presses [[Acknowledge]] and writes a reason of at least 10 characters. The finding stops counting against the status and stays visible, with who acknowledged it. Findings that say the software itself is failing (repeated sync failure, a failed transform, an unverified PDAS write) have no Acknowledge button: they must be fixed. |
| [[Health]] says [[This backup has not been proven restorable. Do not rely on it until it verifies.]] | The newest `.bak` has no matching verification marker, or its size no longer matches the marker. | Run `backup-appdb.ps1` again by hand and read its output. A backup that fails verification is renamed to end in `.unverified`; do not rely on it. |
| [[Health]]'s [[Disk space]] block shows a volume below the warning line | Less than 2 GB is free on the database volume or the backup volume. | Free space, or move backups elsewhere. When it is low, Health reads [[Something needs attention.]]. |
| The recorder line on [[Health]] shows a check-in time that is old | The sync worker has stopped checking in. A recent check-in beside an old newest reading means the worker is fine and the plant simply has nothing new. | Check `SMS-Sync` is running. |
| `epoch:accept` refuses with a message about an old archive, exit 2 | SMS suspects the source is a restored old database, not a new generation. It compares the data itself, because a restore gets today's create date. | Do not override. If the data is IFL's late archive of an existing generation, it belongs with `epoch:backfill` (Appendix B). Use `--i-know-this-is-a-new-generation` only on the maintainer's instruction; every use is audited. |
| A limits change is refused with a message about a large change | The target moved by more than 3 % (or a limit by more than 20 g) in one edit. These two numbers are the developer's defaults. | Tick the large-change box and give a reason of at least 20 characters if the change is intended. See {{ref:pdas-writes}}. |
| A request for a period over a year is refused, "range too large" | Production and weight requests are capped at 366 days. | Ask for a shorter period. |

If a symptom is not listed here, check `GET /api/health` and the [[Health]]
screen first — both are designed to state what is wrong in plain words
rather than a bare error code.
