# Incident record, 2 October 2026: an audit agent emptied the dev app database, and a repo-wide search broke a source copy

**Written 2 Oct 2026 by the documentation pass of the data-trust audit.** Everything below comes from the incident notes the audit kept (`scratchpad/incident/00_INDEX.txt`, `forensic/NOTES.txt`, `restore/01-09*.txt`, `taint.md`), the SQL Server error log and the agents' own transcripts. **Times:** the SQL Server host's local time is **UTC+5**; transcript times are UTC (`Z`). Each time below is given in UTC with the local time beside it where the evidence was local.

**Scope, stated first.** Both events happened on the **owner's development PC** and touched only local databases: the dev app database `sms` and the local copy `DATA_TP1U2_SEP07` of IFL's September sample. **Nothing in IFL's source, on IFL's server or in the plant was touched.** The recovered state was verified by row counts and `DBCC CHECKDB`. Nobody has re-run an end-to-end sync against the real plant.

## 1. What happened

### Event 1: a verification agent ran the real CLI against the live dev `sms` database

- **10:42:32Z (15:42:32 local).** A refuter (task RB1-A) wrote a demo script meant to drive `sms rebuild`, `sms cutover` and `sms retention` against a **fake** database. The script stubbed the CLI's connection with a loader hook that matched the module URL with a regular expression ending in `.js$`; the script imported the modules with a `?x=` query suffix, so the redirect never fired and the real compiled CLI connected as `sms_app` to the real `sms` database.
- **10:42:33Z to 10:43:11Z (15:42:33 to 15:43:11 local).** The CLI executed three `rebuild --all-generations` runs on `sack_event` (`rebuild_audit` ids 10 to 12, snapshot label `sms_20261002_1500`), one `cutover --confirm` with a `./dummy.bak` file the agent had created (**1,162,052 rows cleared**; `app_config` key `cutover.last_utc` written) and two `retention` runs (2 expired sessions deleted). `audit_log` ids 229 to 235 record it.
- **10:44:03Z.** The agent reported it to the orchestrator in an urgent message and stopped. It took no recovery action (it was not allowed to write).
- **Not touched:** `app_user` (7), `sync_run` (16,350), the product, rule and reference tables, and every source database (`DATA_*`, `PDAS_*`).

### Event 2: a whole-repository search raced a SQL open and broke `DATA_TP1U2_SEP07`

- **09:30:42.889Z to 09:32:36.481Z (113.6 s; 14:30:42 to 14:32:36 local).** A refuter (task RB1-B) ran `grep -rln "dq_acknowledgement\|FK_dq_ack" --include=* .` **from the repository root**. `--include=*` matches every file, so the search read every byte of every file under the repo, including the folder holding the extracted September database files (`extracted-sps-2026-09-07/SPS/Backup PDAS  DBs/`).
- **09:32:08.633Z (14:32:08 local).** Another refuter (task RB3-A) ran a read-only `sqlro.sh DATA_TP1U2_SEP07` query. The database was auto-closed (AUTO_CLOSE is ON on every local copy), so SQL Server had to re-open its files.
- **09:32:10.680Z (14:32:10.680 local).** SQL Server logged **Error 17204**: `FCB::Open failed: Could not open file ...\DATA_TP1U2_log.ldf for file number 2. OS error: 32 (The process cannot access the file because it is being used by another process.)`, then errors 5105 and 5170 (twice), and the database went to **RECOVERY_PENDING**. SQL Server opened the data file (file 1) and failed on the log file (file 2). The only error numbers in the whole day's log were 17204, 5105, 5170 and then 104 logins refused (18456, last at 15:40:55 local); there were no 823, 824, 825 or 9001 errors, so no corruption was ever indicated.
- **Evidence the search was the cause, not the SQL query.** The NTFS last-access times on the files in that folder are the footprint of a sequential read: two jpgs at 14:32:04 local, seven jpgs after the folder at 14:32:16, 591 repo files at 14:32:16 and 169 at 14:32:36 (the end of the search). No agent opened the folder by name until 09:33:56Z, after the failure. The earlier open at 14:32:01.64 local, by the same agent, had worked, and the database auto-closed at 14:32:02.46.

## 3. Recovery

1. **Pre-flight, 10:57:28Z.** `audit_log` max id 235, migration 042 present: the 10:55Z state was confirmed unchanged (`restore/01_preflight.txt`).
2. **Safety copy.** The damaged `sms` was backed up and the backup verified (`restore/02`: "The backup set on file 1 is valid").
3. **Restore, 10:58:04Z (15:58:04 local).** `RESTORE DATABASE sms ... REPLACE` from `C:\sms-backups\sms-20260929-212238.bak` (60,834 pages, 4.1 s; `restore/04`, msdb history id 3010).
4. **Migration 042, 10:58:28Z.** The backup predates migration 042 (applied 29 Sep 16:40Z), so `npm run migrate` applied it (`restore/05`: 41 files skipped, 042 applied, "All migrations applied").
5. **Verification.** Row counts per table and per source epoch (`restore/06_verify1.txt`), the 16 epochs by source database, `dq_finding` 33, `app_user` 7, watermarks. **`DBCC CHECKDB` completed** (`restore/07_checkdb.txt`).
6. **`sms_audit`, 10:59:20Z (15:59:20 local).** The same backup was restored again as a new database `sms_audit`, migration 042 applied, and set **READ_ONLY** (`restore/08`, `09`; msdb history id 3011). Every later audit and fix-stage measurement used this copy.

## 4. Prevention (what is now in force)

- **The harness cannot reach `sms`.** `app-harness.mjs` and `services.mjs` force `APP_DB_NAME = sms_audit` before importing anything from the app (a preset `sms` is overwritten), run `SELECT DB_NAME(), DATABASEPROPERTYEX('sms_audit','Updateability')` and throw unless the database is `sms_audit` and READ_ONLY.
- **`sqlro.sh` refuses `-d sms`** (exact name, any case) and refuses SQL text that names the live database (`sms.<schema>.<table>`, `[sms].<...>`, `USE sms`); the `ro-guard` classifier refuses every write, procedure call, transaction and `sqlcmd` directive. `PDAS_WRITE_ENABLED` stays `false` for these runs.
- **The fix-stage preamble** (`scratchpad/fixplan/_PREAMBLE.md`), obeyed by every fix worker, the re-verifier, the gate, the committer and this documentation pass: no database writes anywhere; **never run any SMS CLI command** (`rebuild`, `cutover`, `retention`, `sync`, `epoch:*`, `verify`, `migrate`, `user:*`), prove CLI behaviour with the existing fake-pool unit tests only; **never `grep`, `rg`, `find` or copy recursively from the repo root** or near `extracted*`, `schema_dump`, any `DATA` / `*.mdf` / `*.ldf` folder or `SPS*` (use the Grep and Glob tools scoped to `sms/*/src`); **one SQL file at a time**, with the state of `DATA_TP1U2_SEP07` checked first (`sys.databases` through `master`); workers never touch git state; only the gate builds.
- **Consequence for the code fixes.** The operator-tool fixes of this stage (`rebuild`, `cutover`, `retention`, `verify`, backfill and the DQ checks, `DEFECTS.md` D-62 to D-71) were proven by fake-pool unit tests and read-only SQL demos on `sms_audit`; **none was run live.**

## 5. Open items for the owner

1. **Re-check `DATA_TP1U2_SEP07`.** It was ONLINE when this was written; note that **AUTO_CLOSE is ON for every local copy** (`sms`, `sms_audit`, `DATA_TP1U2`, `DATA_TP1U2_SEP07` and others). That setting is what let one search and one open race. Whether to switch it off for the local copies is the owner's call; it was not changed.
2. **The dev `sms` database is the 29 Sep backup plus migration 042.** The plant simulator's rows after 16:22Z on 29 Sep are not in it; they regenerate if the simulator and the sync worker run. The two sessions created after the backup are gone, so the dev API on :4000 may need a new sign-in; it also still runs the old code until restarted after `npm run build`.
3. **F-15 is unchanged.** The nightly backup runs off this one laptop; every copy of IFL's data and of this deliverable is still on one machine in one building (`ROADMAP-GAP-ANALYSIS.md` section 14). The backups worked on 2 Oct (a verified backup three days old was enough, because only simulator rows and audit-log rows had been written since); an off-machine copy is still missing.
4. **A copy of the damaged state exists** (the safety backup of step 2). If anyone needs the 66 audit-log rows of 29 Sep to 2 Oct, restore that backup into a scratch database, never over `sms`.
5. **Agent policy.** A single agent's own test script defeated its own safeguard (a regular expression over a URL with a query suffix). The harness now makes the live database unreachable rather than relying on an agent's care; the same principle should apply to any future agent run on this PC.
