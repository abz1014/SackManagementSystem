# AUDIT — IFL Sack Management System, 15 September 2026

**Scope:** the whole repository at `floor-first-rework` (`114a8f6`) *plus* the uncommitted working tree — 53,000 lines across five workspaces, 34 migrations, ~24 markdown documents.

**Method:** 39 agents in four stages — six read and mapped a subsystem each (database, ingestion worker, API, web, the uncommitted WIP, documentation-versus-code), three hunted defects (domain correctness, security/data-safety, ops/build/test integrity), 29 re-read every finding against the code trying to **refute** it, one criticised the audit's own coverage and closed its two biggest gaps. 170 findings raised, **156 confirmed, 14 refuted**. Eight of the confirmed highs were re-verified by hand in the source before writing this.

**Independently measured:** `npx vitest run` → **893 passing / 80 files**. `npm run typecheck` → **fails**, one error. `git ls-files` → no secrets, no `dist/`, no `node_modules` tracked.

---

## Verdict

This is a serious, unusually well-disciplined codebase: the hard client constraints are actually enforced in code (not just documented), every production number is traceable to a source row, and the domain hazards this plant creates — an 18-minute acquisition lag, two clocks five hours apart, source tables recreated mid-life with identities restarting at 1, product limits that change over time — are each handled by a named, tested mechanism. The security posture is genuinely good: there is not one string-concatenated SQL statement, not one write to IFL's acquisition database, and not one tracked secret.

The problems are not in the architecture. They are in the **last day of work** and in **the documents**. An unfinished role rename currently breaks the build and locks the engineer role out of two capabilities IFL just granted it; ~990 lines of new service code are reachable from no route; and the document set has drifted far enough from the code that the file designated as "the evidence behind every status" now contradicts the status file that designates it. For a project whose own rule is *"anything claimed must be greppable in the code"*, that drift is the finding that matters most, because it is the one that makes every other claim unverifiable by a reader.

**Nothing found threatens the client's data.** The two absolute constraints — no writes to `DATA_TP1U2`, PDAS write path off — hold in code, verified independently.

# Part 1 — What the system is

## Shape

| Workspace | Lines | Role |
|---|---|---|
| `shared/` | 1,082 | The typed domain: canonical record shapes, five-state cone classification, shift rule, plant clock, config schema |
| `sync-worker/` | 7,725 | Component A — read-only IFL → `sms_raw` → `sms` canonical, on a 60 s loop |
| `cli/` | 2,757 | `sms sync / verify / summary / rebuild / retention / cutover / epoch:* / user:*` |
| `api/` | 25,338 | Express REST over the sidecar only; ~60 routes, ~50 services |
| `web/` | 16,024 | React SPA, no router library — the route is the query string |

One SQL Server sidecar database, two schemas: `sms_raw` (4 verbatim copies of IFL's wide tables) and `sms` (36 tables — configuration, canonical events, versioned rules, audit, auth, PDAS mirrors). 40 `CREATE TABLE` statements across 34 migration files (031 and 032 never existed; the runner sorts by filename and does not check the sequence).

## The data path, end to end

`main()` → `onePass()` → `runPass()` → `runFullSync()` → `runOnce()`, then the transform under a lock:

1. **Connect** to the app DB, then to IFL with at most three retries and *only* if the error classifies as transient (`db.ts:54`). A connect failure writes one `halted` `sync_run` row per configured table and rethrows — a halt is always a database row, never just a log line.
2. **Probe** the source, seed reference rules, mirror PDAS products. The PDAS mirror is deliberately isolated: its failure becomes a standing `product_mirror_failed` finding and does **not** stop ingestion (`pipeline.ts:119-137`).
3. **Per table, in isolation** — resolve the source **generation** ("epoch"), which halts rather than guesses when the generation is unknown or its column fingerprint changed; record non-fatal column drift; read the epoch-scoped watermark `MAX(src_id)`; refuse a source that has gone backwards; read `id > watermark − SYNC_OVERLAP_ROWS` (500); insert verbatim into `sms_raw.*`, skipping rows already present by `(line_id, source_epoch, src_id)`.
4. **Halts are collected and thrown after the healthy tables are written** (`runner.ts:291`), so one dead feed never stops the other three.
5. **Transform** under `sp_getapplock`, incremental on a `transform_wm_*` watermark in `sms.app_config`: map → assign merge keys → dedupe on **our** `raw_id` (never IFL's id, which restarts) → DQ rules → bulk insert → zero-write guard → advance watermark.

**Why the epoch machinery exists:** IFL dropped and recreated its four source tables on 2026-08-05 and every identity restarted at 1. July's 142,511 cones and September's 132,552 coexist under different generations, and `sms verify` reconciles each generation separately against `SUM(id)`.

## The rules the code enforces

The 3 Sep redesign left six rules, each of which exists because it was a real defect. Five still hold; one is broken by the WIP and one is under strain:

| Rule | State |
|---|---|
| One status vocabulary (the scale's bit, and the product's tolerance, named separately) | Holds — `shared/src/domain/classification.ts`, one five-state SQL implementation in `coneState.ts:170` |
| Two clocks, named (production time = plant wall clock labelled UTC; app-written = genuine UTC; five hours apart) | Holds in code — but the design assumes the **host's OS timezone is the plant's**, and the only check for that is optional and commented out in `.env.example` (H7) |
| Detectors ignore the period, using a fixed 14 production days | Holds — `web/src/lib/period.ts` `trailingWindow` |
| The health decision is server-side and measured (freshness from the **oldest** feed, lag measured to a day) | Holds — `live.ts`; and it is the one part of the health logic with **no test** |
| No over-claiming | Holds in the services; two screen headlines now assert "zero production" from a *failed fetch* |
| One station table | Holds — four station *tables* exist but all take rows from one service and one ranking (raised as a violation, refuted) |

Plus the lesson that governs everything time-relative: **this software never sees the present.** IFL's acquisition layer writes a cone's row ~18 minutes after the cone is weighed, so the line is judged against `now − lag`, where the lag is measured from IFL's own insert-versus-production times.

## The screens

Nine views behind `?s=` — Line, Readings, Weight, Rejects, Report, Sacks, plus `setup` (rank ≥ 4), `wall`, `health` — with five drill-down sheets opened by `?sheet=kind:id` over whatever screen is showing, one global period, and one 10 s `/api/live` poll that is the sole source of the plant clock, the current shift, the line state and the health verdict. Every screen is open to every signed-in account (the "one audience" rule); roles gate **writes only**.

# Part 2 — What is actually broken

Eight high-severity issues. The first is the one to fix this hour, because it is also the reason the build is red.

### H1 · The role rename is half-applied — it breaks the build, Setup › People, and the engineer role
`web/src/screens/Setup.tsx:39` · `web/src/App.tsx:78,271,280,319` · `api/src/app.ts:1398` · `db/migrations/035_roles_and_answers.sql:45`

Migration 035 renames rank 1/2 from `operator`/`supervisor` to `viewer`/`engineer`; the API, CLI, `ROLE_RANK` map and eight test files followed. Three things did not:

- **Setup still offers the dead names.** `const ROLES = ['operator','supervisor','manager','admin']` feeds both role `<select>`s. A viewer's role matches no `<option>`, so the browser renders the *first* one — the table displays every viewer as "operator" — and because `defaultValue` never matched, merely **tabbing across the People table fires `PATCH {role:'operator'}` for each row**, which the server rejects 400. Neither new role can be assigned from the UI at all.
- **Two write gates contradict the server.** `canName={rank >= 3}` (Rejects, ReasonSheet) and `canRecord={rank >= 3}` (Sacks) against `requireRole(2)` on `PUT /api/reject-codes/:id` and `POST /api/sacks/movements`. The engineer account — the role IFL's 15 Sep answers put in charge of reject-code naming and sack movements — is shown no control for either. This is the `EXPORT_RANK` defect of 3 Sep reintroduced in the opposite direction.
- **The constant written to fix it was never used.** `const NAME_RANK = ENGINEER_RANK;` at `App.tsx:78` is the single `TS6133` that fails `npm run typecheck` → `npm run build` → `verify:release` → CI.

### H2 · `GET /api/reports/:type` ignores `REPORT_RANK`, and the one protected report is bypassable
`api/src/routes/reports.ts:189` · `api/src/services/reports/common.ts:70`

`REPORT_RANK` declares a rank per report type. `serveReport()` never reads it. `management-summary` is protected only because it is registered as a literal path one line *earlier* — so `GET /api/reports/management%2Dsummary` misses the literal route, matches `:type`, is decoded back to `management-summary` by Express, and serves the manager-only report to a rank-1 account. The next type given rank 3 will be served at rank 1 with no compile error and no test failure. Fix: consult `REPORT_RANK[p.type]` inside `serveReport` after parse.

### H3 · `sms epoch:accept` cannot perform the recovery it documents, and wedges ingestion permanently
`cli/src/commands/epoch.ts:172-198` · `sync-worker/src/epoch.ts:149-156`

On a column type/precision change that does not recreate the table, the worker halts that table every pass and tells the operator to "re-accept the generation". `epochAccept` then, **outside any transaction**, closes the open epoch and *then* inserts a row that violates `UX_source_epoch_identity`. The close has already committed, so the table now has **no open generation**: `resolveEpoch` throws "No open source generation" on every pass, re-running the command fails identically, `epoch:drop` refuses because raw rows exist, and the only exits are hand-written SQL or `epoch:purge` — which deletes that generation's entire history. The same failure hits any repoint back to a server/database/create_date registered once before (dev copy → live → dev copy). **This is on the cutover path.**

### H4 · The Weight control chart judges any past period against the product running *now*
`web/src/api.ts:1229` · `api/src/app.ts:598` · `api/src/services/weightStations.ts:126`

`getWeightStations` sends `trailingDays`/`periodFrom`/`periodTo` — never `from`/`to`. The route therefore defaults its window to `newestProductionDay()`, and the product, its limits, the dashed USL/LSL, Cp/Cpk and the scale-versus-product disagreement counts are all resolved at *that* instant. Pick June or July on Weight and the chart declares those cones in or out of a tolerance that never applied to them — on a line where up to six materials run concurrently with setpoints 10 g apart and ±30/40/50 offsets. The one caveat the screen can show (`limitsChangedInPeriod`) counts version changes of that same product, so it stays 0 and nothing warns the reader. **This violates the project's own rule 1 and rule 3.**

### H5 · One adjustment logged today erases every station's drift history for every past period
`api/src/services/weightStations.ts:116,156` · `api/src/services/calibration.ts:463`

`listCalibrationAdjustments(pool, lineId)` is called with **no window filter**, so it returns the newest 500 adjustments on the line whatever the reporting period. The newest one restarts each station's centreline, and `days.filter(d => d >= adjustedAtMs)` then drops **every** day of a window that ended before it. A September adjustment makes an August report read "no station needs attention, 0 days held" for all fourteen stations. Worst case is the management summary, which computes the *prior* period the same way and reports the delta: `stations_flagged` reads "+3" when nothing changed.

### H6 · The PDAS write surface has grown past the boundary the client was given
`api/src/services/pdasWrite.ts` · `CLAUDE.md:362` · `sms/DEPLOY.md:600` · `api/src/config.ts:179`

`CLAUDE.md:362` states the constraint as `Materials` + its `nhs_events`, "no other table, ever". The working tree now executes **seven** vendor procedures — `CreateMaterial`, `SetMaterialStatusActive`, `AddBlend`, `AddCount`, `AddTubeType`, `CreatePallet`, `SetPalletStatusActive` — across `dbo.Blends`, `dbo.Counts`, `dbo.TubeTypes` and `dbo.Pallets`, while `DEPLOY.md`'s writer-login grant covers **two** of them. Separately, `resolvePdasWrite` checks only that the five writer fields are *present*: there is no allow-list on the PDAS database name and no check that `PDAS_WRITE_USER` differs from `IFL_DB_USER`, so "a separate writer login" is a convention, not a constraint. Everything is still correctly gated by `PDAS_WRITE_ENABLED` and ships off — but the document that defines what was promised to IFL now understates the code by five tables. **Reconcile this before asking IFL for the written authority**, or the authority will be granted for something narrower than what the code does.

### H7 · The two-clocks design depends on the host's timezone, and nothing enforces it
`api/src/index.ts:20` · `.env.example:117` · sync-worker: absent

`plantOffsetMinutes()` reads the OS timezone of whichever process is running and assumes it is the plant's. The cross-check (`PLANT_UTC_OFFSET_MINUTES`) exists, returns early when unset, **is commented out in the shipped `.env.example`**, is absent from `DEPLOY.md`, and does not exist at all in the sync worker that also depends on it. IFL's 15 Sep answer says the owner supplies the PC; a freshly imaged Windows Server defaults to UTC. On such a host every reading arrives "in the future", the worker's DQ flags it, and the live status is wrong by five hours — silently, because the only warning is a log line nobody configured.

### H8 · The configured weight basis is honoured by exactly one service
`api/src/services/reports/coneWeight.ts:88`

`weight_basis` is settable in Setup and declared in every API envelope, but the three report builders and `/api/weights` hardcode or client-source `as_recorded`. It is latent only because 035 chose `gross`, which is arithmetically identical today. The moment an admin selects `net` — a control that ships enabled — the Line and Weight screens and the Sack report disagree about the same kilograms while the envelope declares a basis the figures do not use.

# Part 5 — What is genuinely true

Verified by grep and by reading, not taken on trust. These are the claims a reader might reasonably doubt, and they hold:

- **No write of any kind reaches `DATA_TP1U2`.** Every `INSERT`/`UPDATE`/`DELETE`/`CREATE`/`ALTER` in the repository runs on the app pool or on the explicitly-gated PDAS writer pool. The plant simulator refuses any target not ending `_SIM` and any non-local server.
- **Parameterised SQL everywhere.** No user input is concatenated anywhere in api, cli, sync-worker or scripts; the only interpolated fragments are column/table names from literal allow-lists or an identifier regex.
- **PDAS writes ship off**, behind the flag, through the vendor's own procedures, with one `product_change` row per attempt including the echo-back read.
- **No PLC dependency in any of the five manifests** — still true.
- `createAdapter` throws on an unknown source system; `retention` never touches `audit_log`, `product_change` or any reading; `sack_stock_movement.machine_id` is NULL by CHECK *and* by the only INSERT path, so no sack is attributed to a machine; `audit_log` is append-only at the database.
- **CSV formula injection is handled** (`csv.ts:26` prefixes `=`/`+`/`-`/`@`), and the hand-rolled XLSX writer emits a genuine OOXML package with correct XML escaping — a verifier built a workbook from the compiled output and Windows' own zip reader extracted all seven parts with CRCs intact, with **no npm dependency added**.
- No tracked secrets, no tracked `dist/`, no `TODO`/`FIXME`/`HACK` anywhere in the tree, 893 tests green under both UTC±0 and UTC+5.
